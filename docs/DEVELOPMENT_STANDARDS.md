# Стандарты разработки Asociatii

Эти правила обязательны для изменений приложения, базы данных, инфраструктуры и документации.

## 1. Сначала анализ, затем изменение

Перед реализацией необходимо:

1. Сформулировать проблему и ожидаемый результат.
2. Проверить текущую реализацию, зависимости и уже существующие компоненты.
3. Изучить актуальную документацию установленной версии технологии.
4. Для существенного решения сравнить жизнеспособные варианты, риски, стоимость и влияние на архитектуру.
5. Определить критерии готовности и способ проверки.
6. Для destructive change подготовить перенос данных или доказать отсутствие полезных данных, предусмотреть rollback и получить подтверждение тестами.

Первое найденное решение не принимается автоматически. Если остаётся существенная неопределённость, она явно документируется и решение обсуждается до реализации.

## 2. Удаление ненужного кода и схемы

- Неиспользуемые компоненты, функции, импорты, feature flags, таблицы, колонки и политики удаляются, а не сохраняются «на всякий случай».
- Перед удалением выполняется поиск всех статических и динамических использований, внешних интеграций, SQL-функций, Storage paths и отчётов.
- Удаление таблиц/колонок выполняется отдельной forward-only миграцией после переноса и проверки данных.
- Для рискованных изменений применяется expand → migrate → verify → contract, а не одновременное разрушение старой модели.
- Мёртвый код не маскируется отключением lint rules.
- После удаления обязательны lint, typecheck/build и релевантные unit/integration/RLS/E2E тесты.

## 3. Переиспользуемый UI

Перед созданием компонента необходимо проверить существующие `src/components/ui`, доменные компоненты и patterns.

Общие элементы создаются один раз и переиспользуются:

- таблицы: `DataTable`, column definitions, sorting/filtering/pagination, empty/loading/error states;
- формы: `FormField`, validation messages, sections и action footer;
- поля: input, textarea, select, combobox, date/time, money, file upload;
- feedback: alert, toast, confirmation dialog, skeleton и error boundary;
- layout: page header, breadcrumbs, cards, tabs, sidebars и responsive containers;
- доменные элементы: money, person, property, document, status и audit representations.

Нельзя копировать разметку таблицы, dropdown, modal или поля формы в каждый модуль. Варианты поведения задаются типизированными props и composition, а не копированием компонента.

Переиспользование не означает создание «универсального компонента на всё». Абстракция вводится при повторяющемся контракте; доменная логика остаётся в доменном модуле.

## 4. Единая дизайн-система

- Цвета, размеры, spacing, typography, radii, shadows и состояния хранятся в design tokens/CSS variables.
- Компоненты не используют случайные hardcoded цвета и размеры, если существует token.
- Все состояния имеют единый язык: default, hover, focus-visible, active, disabled, loading, error, warning и success.
- Контраст, keyboard navigation, labels, focus management и screen-reader semantics обязательны.
- Интерфейс поддерживает RO/RU, длинный текст, mobile layout и Europe/Chisinau locale.
- Денежные, датовые и числовые значения форматируются централизованно.
- Изменение темы или brand palette должно выполняться через tokens, а не ручное редактирование десятков компонентов.

## 5. Архитектура и SOLID

Проект остаётся модульным монолитом с едиными границами:

```text
presentation → application/use cases → domain → data/integrations
```

- Single Responsibility: компонент, action или service имеет одну понятную причину изменения.
- Open/Closed: варианты расширяются через composition, стратегии и конфигурацию, без копирования основного flow.
- Liskov Substitution: реализации соблюдают заявленный контракт и одинаковые инварианты.
- Interface Segregation: UI и сервисы получают минимальные DTO/интерфейсы, а не целые database rows.
- Dependency Inversion: доменная логика не зависит напрямую от UI, SDK провайдера или конкретного транспорта.

Дополнительные правила:

- Server Actions считаются публичными mutation endpoints: validation, authentication и authorization выполняются внутри каждого action/use case.
- Доступ к данным централизуется в DAL/repositories; в клиент не передаются лишние поля.
- Доменная логика и финансовые формулы не размещаются в React-компонентах.
- Supabase SDK, платежи, email и Storage изолируются adapter-слоем.
- Cross-tenant безопасность обеспечивается БД/RLS, а не только фильтром приложения.
- Имена, форматирование, структура ошибок и audit events единообразны.

## 6. Структура модулей

Целевая структура каждого зрелого доменного модуля:

```text
src/modules/<domain>/
├── domain/          # entities, value objects, rules, invariants
├── application/     # use cases, DTOs, ports
├── infrastructure/  # Supabase repositories and provider adapters
├── presentation/    # server/client components and view models
└── tests/
```

Shared допускается только для действительно общих контрактов:

```text
src/components/ui/  # design-system primitives
src/lib/            # small cross-cutting infrastructure
src/modules/        # domain ownership
```

Перенос текущего MVP к этой структуре выполняется постепенно вместе с изменением соответствующего модуля, без массового косметического rewrite.

## 7. База данных и Supabase

- Схема изменяется только forward-only миграциями.
- Каждая tenant-таблица имеет tenant key, RLS для всех операций и cross-tenant tests.
- Foreign keys должны сохранять tenant consistency, при необходимости составными ограничениями.
- SECURITY DEFINER функции имеют фиксированный `search_path`, минимальный EXECUTE grant, входную validation и audit.
- Финансовые и юридические данные не редактируются задним числом без version/correction trail.
- Storage private-by-default; доступ проверяется через запись файла и ACL в БД.
- Генерируемые типы БД обновляются вместе с миграцией.

## 8. Definition of Done

Изменение готово только когда:

- выполнены функциональные и security acceptance criteria;
- нет дублирования уже существующего компонента или бизнес-правила;
- удалён заменённый мёртвый код;
- миграция и rollback/recovery path проверены пропорционально риску;
- lint не имеет новых предупреждений, typecheck/build проходят;
- релевантные тесты проходят, включая негативные сценарии;
- документация и ADR обновлены;
- рабочее дерево проверено, изменения понятны из commit diff.

## 9. Документация и области исследования

По необходимости до решения изучаются и фиксируются:

- официальная документация конкретной версии framework/library;
- законодательство Республики Молдова и изменения закона;
- бухгалтерские и налоговые требования с подтверждением специалиста;
- privacy/security standards и threat model;
- продуктовые интервью, рынок и конкурентные решения;
- маркетинг, onboarding, support и эксплуатационные процессы;
- стоимость инфраструктуры и внешних провайдеров.

Исследование отделяет подтверждённый факт, вывод из источников и продуктовую гипотезу.
