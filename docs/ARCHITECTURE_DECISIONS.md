# Архитектурные решения и вопросы для выбора

Статусы: `принято`, `рекомендуется`, `обсудить`, `исследовать`.

## Принято: модульный монолит на текущем этапе

Сохраняем Next.js + TypeScript + PostgreSQL/Supabase как модульный монолит. Предметные модули получают явные границы: identity, associations, property, governance, finance, documents, maintenance, communications, integrations.

Почему: текущая команда и продукт не требуют микросервисной сложности. PostgreSQL хорошо подходит для транзакций, RLS, финансовых связей и отчётности. Границы модулей позволят выделить worker или сервис интеграции позже.

Пересмотр: при доказанной проблеме масштабирования, независимого релиза или нормативной изоляции.

## Принято: private-by-default PostgreSQL и Storage

Supabase Storage остаётся приватным. Доступ строится через таблицу `file_objects` и grants, а не только через первую папку пути. Signed URL короткоживущий. Оригинал, preview и производные файлы имеют отдельные записи. Удаление — soft delete, quarantine и последующее контролируемое уничтожение согласно retention.

RLS deny-by-default. Для каждой новой таблицы обязательны:

- tenant key и внешние ключи, исключающие cross-tenant связь;
- политики SELECT/INSERT/UPDATE/DELETE;
- тесты «пользователь A не видит/не меняет tenant B»;
- проверка service-role путей;
- аудит привилегированной операции.

## Рекомендуется: финансовый subledger внутри продукта, официальный учёт через интеграцию

Вариант A — построить полный бухгалтерский ERP. Максимальный контроль, но высокий юридический риск, большой объём форм и постоянное сопровождение законодательства.

Вариант B — только интеграция с 1C/другой системой. Быстрее, но невозможно прозрачно объяснить начисления и долги собственнику без дублирования логики.

Рекомендация — гибрид: собственный double-entry operational subledger для начислений, платежей, фондов и сверки; утверждённый экспорт/API в бухгалтерскую систему, где формируется официальная отчётность. После пилота решаем, расширять ли ядро до полного учёта.

Требуется обсудить с бухгалтерами: 1C конфигурации, используемые APC; WinMentor/другие продукты; план счетов; формат обмена; ответственность за закрытие периода.

## Обсудить: платежный провайдер

### MPay/MIA

Плюсы: локальная узнаваемость, разные инструменты оплаты, подтверждение в реальном времени. Минусы: требуется договор/одобрение, коммерческая модель и API должны быть подтверждены.

### Лицензированный PSP/card acquiring

Плюсы: быстрый checkout и SDK. Минусы: комиссии, chargeback, PCI scope и сверка.

### Bank transfer/MIA QR per association

Плюсы: деньги идут непосредственно на счёт APC, меньше custody риска. Минусы: различия банков, reconciliation и onboarding.

Рекомендация для пилота: уникальный reference + MIA QR/банковский перевод на счёт APC, импорт выписки и ручная сверка с подсказками. Параллельно получить условия MPay и минимум двух PSP/банков.

## Обсудить: юридическая электронная подпись и идентичность

### Email/password + OTP

Подходит для обычного кабинета, но не доказывает квалифицированную подпись.

### MPass/MSign или квалифицированный trust provider

Выше юридическая доказательность, но зависят от доступности интеграции, стоимости и UX.

### Смешанная модель

Рекомендация: обычная сильная аутентификация для повседневных действий; квалифицированная подпись/доверительная услуга для протоколов, заявлений и выбранных решений. До интеграции система формирует пакет для внешнего подписания и проверяет подписанный файл.

## Обсудить: фоновые задачи и realtime

Вариант A: Supabase Edge Functions + Cron — меньше инфраструктуры, подходит для простых задач.

Вариант B: Inngest/Trigger.dev — удобные retries, observability и workflow, но новый vendor.

Вариант C: PostgreSQL queue + отдельный worker — контроль и переносимость, но больше эксплуатации.

Рекомендация: PostgreSQL outbox как источник истины плюс небольшой worker. Провайдера исполнения выбираем после прототипа уведомлений, ежемесячного billing run и импорта банка.

## Обсудить: hosting и регион данных

Текущие Vercel + Supabase эффективны для MVP. До пилота сравнить:

- Supabase Cloud EU + Vercel EU execution;
- self-hosted Postgres/Storage в EU;
- другой managed Postgres + S3-compatible private storage.

Критерии: местонахождение и субобработчики данных, DPA, backup/PITR, RTO/RPO, private networking, audit logs, экспорт, стоимость на 100/1 000/10 000 APC. Миграция ради абстрактного контроля не выполняется без измеримого выигрыша.

## Рекомендуется: PWA сначала, native позже

Responsive web/PWA покрывает собственников и администратора быстрее. Push, камера для счётчиков/дефектов и offline draft реализуются через PWA. Native React Native/Flutter рассматривается после подтверждения, что ограничения iOS/Android мешают активации или эксплуатации.

## Рекомендуется: документы без AI в контуре принятия решения на первом этапе

OCR и AI могут извлекать реквизиты invoice или предлагать категорию, но результат подтверждает человек. Модель не создаёт проводку, начисление, юридическое решение или платёж без review. Исходный файл, результат извлечения, версия модели/правила и подтверждающий пользователь сохраняются.

## Целевые системные свойства

- Доступность пилота: 99.5%; после финансового запуска — 99.9% для кабинета и API.
- RPO: не более 15 минут для транзакционных данных; RTO: 4 часа на пилоте, затем 1 час.
- Все денежные суммы — integer minor units или NUMERIC с валютой; JavaScript float запрещён.
- Все timestamps хранятся UTC, отображаются Europe/Chisinau; юридические даты сохраняют исходную timezone.
- Идемпотентность обязательна для billing run, webhook, импорта банка, генерации документа и отправки уведомления.
- Audit trail append-only; бизнес-события не удаляются каскадом без retention review.
- API и exports версионируются; схема БД меняется forward-only миграциями.
- Наблюдаемость: correlation id, structured logs без PII, error tracking, job dashboard и security alerts.
